# 도메인 정책

**기준 문서: 노션 API 명세**(프론트 합의본). 이 문서와 충돌하면 노션이 우선이며, 확인 즉시 이 문서를 고친다.
그다음 기획 자료 우선순위: ① 최신 화면명세서 ② 정책 문서·개발 확정안 ③ 이전 `Billage_IA v0.4`.

## 도메인 구조와 관계

```text
모임(GroupSpace) 1 ─ N 모임 관리자(GroupMembership) ─ 1 가입 사용자(User)
모임(GroupSpace) 1 ─ N 모임원 명단(Member)          ← 회비 납부 대상, 계정 없음
모임 1 ─ N 폴더(Folder) ─ N 하위 폴더(중첩 지원)
폴더 1 ─ N 장부(Ledger) 1 ─ N 수입·지출 내역(Entry)
모임 1 ─ N 회비 회차 1 ─ N 청구(Member 기준) 1 ─ N 납부 기록

※ GroupMembership(권한)과 Member(납부 명단)는 별개이며 자동 연결하지 않는다.
```

앱 GNB: 대시보드 / 내역 / 폴더 / 납부관리 / 더보기

## 엔티티

### User
- 서비스 가입 계정. 이메일/비밀번호(BCrypt) 또는 소셜 로그인(구글·카카오)으로 생성. 소셜 전용 계정은 비밀번호 없음.
- **이름 최대 10자**(기획 글로벌 정책). `entry.created_by_name` · `approved_by_name` 스냅샷이 10자라
  이 값을 넘기면 내역 저장이 깨지므로 가입 단계에서 막고 컬럼도 10자로 맞춘다(V9).

### SocialAccount
- User와 소셜 Provider 연결. 한 User가 구글·카카오 모두 연결 가능. `(provider, providerUserId)` 유일.

### GroupSpace
- 하나의 동아리/모임. `Group`은 Java/SQL 충돌 위험 → 엔티티명 `GroupSpace`, API는 `/groups`.

### GroupMembership (모임 관리자)
- 가입 사용자(User)와 모임의 **권한 관계**. 앱에 로그인해 모임을 쓰는 주체.
- 역할: `OWNER`(총무) / `MEMBER`(일반 권한 관리자) 2단계. 커스텀 권한 없음.
  공동 총무 수 제한 없고 **항상 최소 1명의 OWNER** 필요 → 마지막 총무의 권한 해제·탈퇴는 `LAST_OWNER_REQUIRED(409)`.
- 모임 생성자 = OWNER, 초대 코드 참여자 = MEMBER.
- 일반 권한 관리자는 폴더·장부 이름 수정/삭제 불가, 내역 등록 시 승인 요청(PENDING) 흐름을 탄다.

### Member (모임원 명단)
- **회비 납부 대상 명단**. 총무가 등록하며 권한 값을 갖지 않는다.
- 초대 코드로 참여한 관리자는 이 명단에 **자동 추가되지 않는다**. 계정과 자동 연결하지도 않는다.
- 회비·납부 이력은 User가 아니라 **Member 기준**으로 연결한다.
- 삭제 시 회비 참여 데이터까지 완전 삭제하며, 관리자 권한에는 영향을 주지 않는다.
- 동명이인을 허용한다. 이름에 유니크 제약을 두지 않는다.

**필드**(2026-08-23 기획 확정 — 모임원 추가·상세 수정 화면)

| 필드 | 필수 | 제한 | 비고 |
| --- | --- | --- | --- |
| 이름 | O | 10자 | |
| 전화번호 | X | 숫자 9~11자리 | 하이픈을 넣어 보내도 서버가 **숫자만 남겨 저장**한다. 표기는 화면이 만든다 |
| 태그 | X | 개당 10자, 최대 10개 | **모임원마다 자유 입력**. 모임 단위 태그 마스터 테이블은 두지 않는다 |
| 메모 | X | 30자 | |

- 전화번호 노출 범위는 **관리자 전원 동일**(일반 권한 관리자도 그대로 본다, 기획 확정 2026-08-23).
- 태그는 `member_tag(member_id, name)` 복합 기본키라 같은 태그를 두 번 붙일 수 없다.
- **개별 추가** `POST /groups/{groupId}/members` — 위 4개 필드.
- **일괄 추가** `POST /groups/{groupId}/members/bulk` — **이름만** 받는다. 입력 텍스트를
  쉼표·띄어쓰기·줄바꿈(`[,\s]+`)으로 잘라 각각을 독립된 모임원으로 저장한다. 1회 100명 상한.
  하나라도 규칙에 어긋나면 전부 취소된다(한 트랜잭션).
- **상세 수정** `PATCH /groups/{groupId}/members/{memberId}`(총무 전용). 수정 화면이 항목 전체를 담아
  보내므로 **부분 수정이 아니라 통째 교체**다 — 전화번호·태그·메모를 빼고 보내면 그 값은 비워진다.
  이름 수정 시에도 회비 참여 데이터는 유지된다. 오타를 고치려고 삭제 후 재등록하면 납부 기록이 함께 사라지기 때문.

### GroupInvitation
- 총무가 발급하는 모임 초대 코드. 유효 기간 7일, 만료 전까지 여러 명이 사용 가능(1회용 아님).
- 참여 링크는 `billage://groups/join?code={code}` 형식.

### Folder (폴더)
- 장부를 묶는 **계층 구조**. `parentFolderId` 가 null 이면 최상위. 중첩 지원.
- 이름 최대 20자. 삭제 시 내부 장부·하위 폴더는 상위 폴더로 이동하고 폴더만 제거한다.
- 이동 시 자기 자신·자기 하위 폴더를 상위로 지정하면 `INVALID_PARENT_FOLDER` 로 막는다.
- **`parentFolderId` 는 3가지 상태를 구분한다** — 미전달(이동 안 함) / JSON `null`(최상위로 이동) / 값(그 폴더로 이동).
  이 구분은 `spring.jackson.deserialization.use-null-for-missing-reference-values` 설정에 의존한다.
  끄면 Jackson 3 기본값상 미전달도 `Optional.empty()` 가 되어 **이름만 수정해도 폴더가 최상위로 올라간다.**
- **알려진 한계(MVP 허용)**: 순환 검사는 검사 시점 상태만 본다. 두 사용자가 A→B 아래, B→A 아래로 **동시에** 이동하면
  둘 다 통과해 순환이 남을 수 있다(각자 다른 행을 수정하므로 `@Version` 도 못 막는다).
  막으려면 이동 시 조상 경로 비관적 락이나 모임 단위 직렬화가 필요한데 MVP 범위를 넘어 넣지 않았다.
  대신 최악의 증상만 차단해 뒀다 — `Folder.depth()` 는 방문 집합으로 순회를 끊어 무한 루프에 빠지지 않는다.
  (순환이 생기면 `getFolderTree` 응답에서 해당 폴더들이 조용히 누락된다.)

### Ledger (장부)
- 폴더에 속하는 장부. 이름 최대 20자, 예산(`budget`)은 월별이 아니라 **장부 전체 기간 총예산**(0 ~ 999,999,999, 미설정 가능).
- 삭제 시 장부와 종속 내역을 완전 삭제한다. 폴더 이동은 **같은 모임 안에서만** 가능(`GROUP_MISMATCH`).
- `folderId` 는 nullable — 최상위 폴더가 삭제되면 그 안의 장부는 폴더 없는 **최상위 영역**으로 올라온다.
- 잔액·집계는 저장하지 않고 승인된 내역으로 매번 계산한다(`LedgerStats`).

### Entry (내역)
- 수입/지출 내역. 금액 `BIGINT`(원화), **항상 양수**, `type` = INCOME | EXPENSE, 최대 999,999,999.
- 제목 최대 20자, 메모 최대 30자.
- 상태: `PENDING → APPROVED` 두 가지만. **반려(REJECTED)는 MVP 제외**.
- 일반 관리자 등록 → `PENDING`, 총무 등록 → 즉시 `APPROVED`(기획 글로벌 정책 확정).
- **APPROVED만** 잔액·통계·보고서에 반영.
- 회계 이력의 행위자는 Member 명단이 아니라 **User 기준**으로 기록하고, 작성자·승인자 이름은 그 시점 값을 함께 보존해 탈퇴 후에도 표시가 깨지지 않게 한다.

### UploadedFile (파일)
- 메타데이터만 DB에 저장 (용도, storage key, 원본 파일명, 타입, 크기, 업로더). 바이너리는 저장소에 둔다.
- 용도: `RECEIPT`(증빙) / `PROFILE_IMAGE` / `GROUP_IMAGE`. 현재 내역 연결은 RECEIPT 만 구현.
- 허용 형식 jpg·jpeg·png·webp, 최대 10MB (`billage.file.*` 설정, 기획 확정 시 조정).
- 원본 파일명을 storage key 로 쓰지 않는다(`{용도}/{yyyy/MM/dd}/{UUID}.{확장자}`).
- 접근: 연결 전에는 업로더만, 내역에 연결되면 그 모임 관리자면 조회 가능. 삭제는 업로더만, 연결된 파일은 `FILE_IN_USE`.
- 저장소는 `FileStorage` 인터페이스 뒤에 있다 — 로컬 개발은 디스크, dev·prod 는 S3.
- 다운로드(`GET /files/{id}/content`)는 권한 검사 후 **presigned URL 로 302 리다이렉트**한다(로컬 디스크는 직접 전송).

## 내역 승인 정책

- 일반 권한 관리자 등록 → `PENDING`, 총무 등록 → 즉시 `APPROVED`. 승인은 총무만(`POST /entries/{id}/approve`).
- 이미 승인된 내역을 다시 승인하면 `ENTRY_ALREADY_APPROVED(409)`.
- **내역 수정·삭제는 총무(OWNER) 전용**(기획 확정 2026-08-17, 2026-08-18 재확인).
  일반 권한 관리자는 **본인이 등록한 승인 대기 내역도** 고치거나 지울 수 없다 —
  기획 표현으로 "**승인 요청하기를 누른 순간 손을 뗐다고 생각하면 된다**". 이후는 총무의 몫이다.
  같은 이유로 백업·내역·장부 삭제도 총무만 할 수 있고, 그래서 공동 총무 권한 부여가 존재한다.
- 총무는 승인 대기 내역을 직접 수정할 수 있고, 승인 완료 내역도 수정 후 재승인을 요구하지 않는다.
- 승인 후 수정·삭제해도 `PENDING` 으로 되돌아가지 않는다. 유형(`type`)은 수정할 수 없다.
- 수정 시 `receiptFileIds` 를 보내면 증빙 **전체 교체**다 — 목록에서 빠진 증빙은 저장소에서도 삭제된다.
  필드를 보내지 않으면(null) 기존 증빙을 유지한다. 내역을 삭제하면 연결된 증빙도 함께 삭제된다.
- 반려 API와 `REJECTED` 상태는 제공하지 않는다 — 부족한 내역은 총무가 고쳐서 승인.
- 주요 엔티티에 `@Version` 낙관적 락.

## 잔액·보고서

- 잔액 필드 저장 금지. 항상 `승인된 수입 합계 - 승인된 지출 합계`로 계산.
- 대시보드는 모임의 **전체 장부**를 합산하며 총무·일반 권한 관리자에게 동일한 데이터를 준다.
  `recentEntrySize` 는 1~20(기본 5), 벗어나면 `INVALID_QUERY_PARAMETER`.
- 대시보드·보고서 동일 집계 기준(**승인분만**). 초기엔 SQL 집계 쿼리만 — 성능 문제가 실측되기 전 집계 테이블/Redis 금지.

### Report (보고서)

- 보고서는 **생성 시점 스냅샷(고정본)**이다(노션 명세 기준). 실시간 재집계가 아니다.
  `report`(요약) → `report_ledger`(장부별 합계) → `report_entry`(내역 한 줄) 3단으로 값을 복사해 저장한다.
- 원본 `ledger_id`·`entry_id` 는 참고용으로만 남기고 **FK 를 걸지 않는다** — 원본이 삭제돼도 스냅샷은 유지돼야 한다.
  표시 금액·문구는 항상 스냅샷 컬럼 값을 쓴다.
- 대상 내역은 선택한 장부의 기간 내 **승인(APPROVED)** 내역뿐이다. 기간에 승인 내역이 하나도 없으면
  `REPORT_RANGE_EMPTY(422)`. 선택했지만 기간에 내역이 없는 장부는 0원으로 포함한다.
- 잔액은 여기서도 저장하지 않고 `total_income - total_expense` 로 계산한다(합계 자체는 스냅샷이라 저장).
- 수정·삭제 API 는 없다. **모임 Hard Delete 시에만 함께 삭제**된다.
- MVP 에서 PDF·Excel 생성과 다운로드 URL 은 제외 — 웹뷰 렌더링용 JSON 만 반환.
- 권한 **확정**: 목록·상세 조회 `MEMBER` / 생성 `OWNER`
  (기획 「일반 권한 모임 관리자」 — "총무만이 보고서를 생성할 수 있으며 일반 권한 회원은 만들어진 보고서를 볼 수 있음", 2026-08-17).

## 납부 관리 (구현 완료, 2026-08-19)

기획이 "납부 관리 주요 기능의 정책이 마무리되지 않았으니 최대한 마지막으로 착수해달라"고 한 영역이다.
2026-08-18 기획 답변으로 핵심 3건이 확정되었다. 노션 Dues 명세를 먼저 확인할 것.

납부 관리의 전제: **거래내역 자동 등록이 안 되는 런칭 버전에서 이 기능은 총무가 수기로 정리하는 보조 도구다.**
납부 완료 전환도 "총무가 리스트를 옮긴 행위"일 뿐 실제 입금과 연동되지 않는다. 그래서 정합성을 지키겠다고
총무의 조작을 막지 않는다 — 어긋난 부분은 총무가 수기로 맞춘다.

- 납부 대상은 **Member 명단** 기준. 상태값은 `UNPAID / PAID` 2단계다. 부분·초과 납부는 미지원.
- 회비 생성·수정·삭제·마감·납부 상태 변경은 전부 **총무 전용**(일반 권한 관리자 전면 금지). 조회만 `MEMBER`.
- 마감은 **전원 `PAID`** 여야 가능하고, 그때 선택한 장부에 회비 제목 + 총 모인 금액으로 `INCOME` 내역 1건을 만든다.
  개별 입금 건으로 쪼개지 않는다. 이 내역은 **총무의 행위이므로 즉시 `APPROVED`** 다.
- **마감 전이면 금액을 제외한 모든 값을 수정할 수 있다.** 이미 `PAID` 인 대상자를 대상에서 빼는 것도 막지 않는다.
  빼면 **총 회비 금액이 그만큼 달라지는 것이 정상 동작**이며(총액 = `PAID` 인원 × 금액), 보정은 총무가 수기로 한다.
- 모임원(Member)을 명단에서 지우면 그 사람의 회비 참여 데이터도 **완전 삭제**된다.
- 대시보드의 회비 집계는 **진행 중(OPEN) 회비만** 센다 — 마감분은 이미 장부 내역으로 반영돼 있어 이중 집계가 된다.
- 회비 삭제는 납부자가 있거나 마감된 뒤에도 가능하다. 마감으로 생긴 수입 내역은 건드리지 않는다.

### 마감 회비와 수입 내역의 분리 (2026-08-18 확정)

**회비가 마감되는 즉시 회비와 그 수입 내역은 서로 독립된 데이터가 된다.**
회비를 삭제해도 **수입 내역은 장부에 그대로 남는다.** 반대로 내역을 지워도 회비는 남는다.

기획 근거: 마감된 회비가 계속 쌓이는데 내역과 묶여 있으면 회비를 편히 지울 수 없어 처치 곤란해진다.

구현 지침:
- 내역에서 회비로 가는 참조는 **약한 연결**이어야 한다 — FK 로 묶어 연쇄 삭제되게 하지 말 것.
  회비가 사라지면 그 내역은 그냥 평범한 수입 내역이 된다.
- 화면에서 "납부관리 아이콘 + 회비 상세로 뎁스인"은 **회비가 살아 있을 때만** 성립하는 표시다.
  회비가 지워진 뒤에도 그 링크가 남아 깨지지 않도록 해야 한다.
- 이전에 이 문서에 "함께 삭제로 가정"이라 적었던 것은 **틀렸다**(기획 답변으로 반대로 확정).

아직 확인 필요:
- 마감 취소(재오픈) API 존재 여부. 현재 명세에 없어 실수 복구 경로가 회비 삭제뿐이다.

## 삭제 정책

| 대상 | 정책 |
| --- | --- |
| 내역 | 승인 상태와 무관하게 완전 삭제. 별도 이력 보존 없음 |
| 장부 | 장부와 종속 내역을 완전 삭제 |
| 폴더 | 내부 장부·하위 폴더를 상위로 이동하고 폴더 구조만 제거 |
| 모임원(Member) | 완전 삭제. 회비 참여 데이터도 함께 삭제. 관리자 권한에는 영향 없음 |
| 모임 탈퇴 | GroupMembership 만 삭제. 납부 명단은 자동으로 찾아 지우지 않음 |
| 모임 | 완전 삭제. 관리자·명단·초대 코드·폴더·장부·내역·회비·보고서까지 전부 삭제 |

전 영역 Hard Delete 로 확정(2026-08-16, 노션 API 공통 규칙 17장 기준).
보고서는 생성 시점 스냅샷이라 원본 내역 수정·삭제에는 영향받지 않지만, **모임 삭제 시에는 함께 삭제**한다.

## 인증

- Access Token = JWT / Refresh Token = DB 저장, 재발급 시 회전 + 이전 토큰 폐기, 로그아웃 시 폐기.
- 인증 기능을 다른 도메인 엔티티에 강하게 결합하지 않는다.

### 간편 로그인(구글·카카오)

- 클라이언트(RN 앱)가 각 Provider SDK로 로그인해 얻은 토큰(구글 ID Token, 카카오 Access Token)만 백엔드로 전달 —
  백엔드는 OAuth Authorization Code Flow를 직접 처리하지 않는다.
- `POST /api/v1/auth/social/login`: `(provider, providerUserId)`로 연결된 계정이 있으면 즉시 로그인.
  없으면(최초 로그인) 토큰만 저장하지 않고 이메일만 응답해 클라이언트가 약관 동의·이름 입력 화면으로 이동하게 한다.
- `POST /api/v1/auth/social/signup`: 약관 동의 + 이름을 받아 가입을 완료하고 즉시 로그인 처리.
  Provider 토큰을 재검증하며(상태를 서버에 보관하지 않음), 같은 이메일의 계정이 이미 있으면 새로 만들지 않고 거기에 연결한다
  (Provider가 이메일 소유를 검증했으므로 안전하다고 간주).
- 약관 동의는 버전 이력 없이 `User.termsAgreedAt` 시각만 기록(초기 단순화, 약관 개정 이력 추적 필요해지면 별도 테이블로 분리).
- 이메일/비밀번호 로그인은 당분간 함께 유지.
